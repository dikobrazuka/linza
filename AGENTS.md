# AGENTS.md — обязательные правила для Codex и других разработчиков LINZA

**Важная цель:** сделать рабочий русскоязычный сайт управления проектом LINZA, а не ещё один статичный текстовый лендинг. Сначала читать этот файл и `docs/SITE_SOURCE_OF_TRUTH.md`. Приоритет: корректность фактов, работоспособность сайта, сохранение пользовательского прогресса, удобство использования на ПК/мобильном.

## Сайт: какие страницы

- `site/index.html` + `site/work.js` + `site/work.css`: понятный обзор проекта, три независимых образца, ближайшие действия и ссылки на инструкции.
- `site/board.html` + `site/board-upgrade.js`, `site/team-addon.js`, `site/drone-addon.js`, `site/shell-addon.js`: подробный WBS, Kanban и интерактивный бюджет. Это legacy/localStorage код — модернизировать осторожно, НЕ стирать существующие данные пользователя.
- `site/explain.html` + `site/explain.js` + `site/explain.css`: интерактивная наглядная физика/масштабирование/стенд. Все расчётные примеры отдельно помечать.
- `site/team.html`: пока перенаправление на index.html, не выводить как самостоятельную готовую страницу.
- `.github/workflows/pages.yml`: публикация **папки `site/`** через GitHub Pages. Отсюда относительный путь к JSON **`./data/project.json`** и т. д.

| Ветка | Диаметр | Частота | Статус |
|---|---:|---:|---|
| PLA/FDM | **200 мм** | **5 ГГц** | План нового демонстратора |
| HARZ DE-10 / photopolymer | **120 мм** | **5 ГГц** | Отдельный материал/модель |
| Заказная | **80 мм** | **24 ГГц** | Отдельная конечная конструкция; ≤300 г |
| CDM324 | встроенная антенна | ~24.125 ГГц | только аналоговый Doppler IF, **не измеритель RCS** |

- Смета корзины 09.11.2026: **24 267 ₽**, 32 строки.
- План DE-10 1 кг: **14 000 ₽** отдельно, итог только известных статей **38 267 ₽**, без оснастки/доставки/TBD и **без подтверждения покупки**.
- Изменение `S21` в помещении не равно автоматически доказанной ЭПР, CDM324 не измеряет дальность/абсолютную RCS.
- Не путать 5-ГГц рупор с 24-ГГц встроенной антенной CDM324.
- Для 5-ГГц NanoVNA **не использовать** старый слот калибровки 383–483 МГц.

## Архитектура данных: что должен сделать Codex

1. UI должен загружать JSON из `site/data/project.json`, `site/data/actions.json`, `site/data/procurement.json` и иметь понятную fallback-обработку ошибки загрузки.
2. Никогда не задавать 24 267 ₽/32 строки только как DOM-текст, если есть реальная структура JSON: вычислять суммарную стоимость `rows.reduce((a,r)=>a+r.line_total_rub,0)`, отдельно смолу и дополнительные TBD.
3. Разделить **плановую закупку** и **личный черновик**. Legacy `defaultBudget` в `board.html` — **старый пример, НЕ актуальная закупка**. Нельзя отображать его сумму под названием «общая смета».
4. Разделить **канонические задачи** и **личные отметки**. Данные из файлов — план; прогресс в localStorage — локальные пользовательские данные. При миграции сопоставлять по стабильному `id`, не затирать сохранённые статусы/добавленные задачи без резервной копии и явного согласия.
5. При отсутствии сервера на GitHub Pages нет синхронизации между устройствами. Не обещать общую командную синхронизацию статусов: для неё нужен сервер или аутентифицированный API. Пока экспорт/импорт JSON с объяснением ограничений.
6. Страницы содержат ссылки прямо на нужный Markdown (сборка рупора, пайка, BOM, опыт PLA, опыт DE10, Ø80); добавить хлебные крошки/аккордеоны/пошаговые чек-листы и чёткие критерии GO/STOP.
7. Статусы `planned`, `blocked`, `done` использовать корректно; **нет подтверждённых физических замеров**. Не превращать тестовый/демонстрационный график в эксперимент.
8. НЕ перезаписывать site/board.html целиком, не удалять сохранённые ключи `linza-wbs-v1`, `linza-budget-v1`, `linza-budget-reserve-v1`. Миграция должна быть проверяемой, бэкап старого состояния перед преобразованием.
9. Никаких выдуманных источников, цен, характеристик SMA, реальной ε, результатов +10 дБ или потерь. Если поле неизвестно, показывать `TBD` с ссылкой на действие для проверки.

- На сайте чётко видно: выполнено, запланировано, заблокировано; изменённые в браузере поля **не превращаются автоматически в коммит GitHub**.

- Поставить тесты данных (`node --check site/*.js`; JSON parse; 32 строки, сумма 24267, отсутствие подмены Ø200 DE-10; pytest для Python). Не объявлять окончательную готовность, пока не зелёный CI и не проверена интерактивность в браузере.
- Не отказываться от работы после правки документации: нужно **запустить сайт/пройти UI end-to-end** и проверить соответствие текущим JSON.
- При изменениях данных обновлять JSON и первичные Markdown **в одном pull request/коммите**, а не вразнобой.
